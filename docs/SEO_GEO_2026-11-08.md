# LYnto search visibility and reliability work — 8 November 2026

Status: implemented in a review branch and tested locally. This document does not assert that the changes are live. Deployment needs the existing Cloudflare account. No production database migrations, prices, product approvals, orders, receiving accounts or credentials were changed.

## Evidence from the live site

The public sitemap contained 350 unique URLs: 163 products in Arabic and English, 4 translated categories, and the other public pages. A first pass at six concurrent requests returned 271 successful HTML responses and 79 HTTP 503 responses whose bodies said `error code: 1102`. This is a crawl sample, not a visitor error rate. Two failed URLs later returned 200 with cache hits; the failures are intermittent. Cloudflare identifies 1102 as a Worker CPU/memory resource-limit error. Production runtime metrics are needed to distinguish the exact limit and confirm improvement after deployment.

Browser checks reproduced these defects:

- Home → product navigation retained the homepage canonical, description and Open Graph URL.
- Cart → Products navigation retained `noindex,nofollow` on the public catalog.
- The linked `/manifest.webmanifest` returned 404.
- `/llms.txt` returned an empty HTML app shell with HTTP 200, not a text document.

HTTP/source inspection also found:

- Every product lookup loaded the entire published catalog and all its approved plans, then searched the array. Rendering created repeated number formatters and tested image existence through an asset fetch.
- `/api/public/products` returned 743,950 uncompressed bytes for 163 products, including full bilingual descriptions, requirements and complete plans. Listing cards do not need that data.
- `robots.txt` blocked the public bootstrap/product endpoints used to render the page after React replaced the initial HTML.
- Arabic Product structured data used English names/descriptions. Products used AggregateOffer instead of this store's individual plan offers.
- Support, about and policy HTML contained little more than headings or a generic description until JavaScript ran.
- The security policy blocked the existing Cloudflare Analytics script origin.
- The source contained product cards for 74 of the 163 live products, leaving 89 without their expected card assets.

Existing strengths were preserved: real server-side product text, reciprocal language URLs, canonical host handling, real 404 page status, private order links, protected admin access, manual transfer verification, and integer-piastre pricing.

## Implemented changes

1. Product details query only the requested published, supply-validated product and its approved priced plans. Draft and unvalidated products stay private. SQL now provides lightweight card projections and category counts. Sitemap generation loads slugs and timestamps instead of all descriptions/plans.
2. Catalog screens request `?view=cards`; the existing full public catalog endpoint remains compatible. Based on the same live 163-product data, the projected card JSON is approximately 95,502 bytes, 87.2% smaller than the full response. This is a payload comparison, not a measured page-speed or conversion improvement. Bootstrap also returns only the fields used by featured cards.
3. Currency formatters are reused rather than recreated for every price. No monetary arithmetic or stored prices changed.
4. Shared metadata builders keep server HTML and SPA navigation aligned: titles, descriptions, robots, canonical, language alternatives, social previews and JSON-LD. Private routes, draft previews, missing pages and staging retain exclusion. Navigating back to a public page clears stale private metadata.
5. Product markup uses localized descriptions and actual per-plan Offer records with EGP prices, availability and a working plan-selection URL. Product query URLs canonicalize to the main product. No fabricated reviews, ratings, GTINs, discounts or return conditions were added. Markup is not a guarantee of Google Shopping/Merchant Center eligibility; evaluate digital-product eligibility separately before submitting feeds.
6. About, FAQ, guarantee and purchase-policy facts are present in initial HTML. Policy summaries preserve the existing published business terms. Organization data uses the actual public contact/social settings and consistent identifiers.
7. Two original guides in Arabic and English explain LYnto's transfer/verification/delivery process and gift-card region checks. The same article data drives visible pages and initial HTML, with sources, review dates, Article/Breadcrumb markup and links to relevant products. Header, home and product links make the guides discoverable. Guides do not claim that original software providers accept InstaPay directly.
8. Stable language URLs replace device/bot-based forced redirection. Visitors can still switch languages explicitly.
9. The real manifest is served; missing assets return actual 404s. `/llms.txt` is an optional plain-text orientation document, with no private data or stale price feed. It is not treated as a ranking mechanism or a prerequisite for AI visibility.
10. Robots permits the public rendering dependencies and continues to exclude private APIs/order flows. Public JSON responses carry a noindex header. The analytics script's specific origin is allowed without enabling unsafe inline script execution.
11. Added a build-time source manifest that generates 89 full-size product cards and 89 thumbnails using the existing visual template and public product names. They use monograms where a platform logo is unavailable; they do not imply official endorsement. Existing tracked cards were preserved; new JPEG derivatives are generated during the build instead of stored in Git. Build-time image indexing avoids per-page asset probes and references real image files.

## Validation

- `npm run typecheck`: application and Worker types pass.
- `npm test`: 33 tests pass, including real SQLite eligibility queries over a 200-product fixture, money/DST tests, schema/canonical/privacy checks, and actual React/DOM navigation regression tests.
- `npm run build`: production client and Worker build pass.
- `npm run test:seo`: 10 isolated built-Worker integration checks pass using Miniflare, actual initial HTML and local seeded D1. They cover offers/languages, policy/FAQ text, guides, robots, sitemap, manifest, 404s, private pages, light payloads and the analytics security policy.
- Production purchase flows were not submitted and no real customers were messaged.
- A full browser preview could not start in this environment because Vite's inspector-port discovery could not enumerate network interfaces. DOM navigation was tested with Happy DOM; the built Worker ran in Miniflare. Full responsive visual QA and live CPU/Core Web Vitals improvements remain to be verified after deployment.

## Deployment and measurement

Use the existing Cloudflare production project and secrets. Do not create a replacement site, reset the database, publish example prices, replay seed migrations, or expose order/admin data. These source changes require no new database migration. Review the branch, deploy through the current authorized Claude Code/Cloudflare setup, and then:

1. Re-fetch representative product/category/policy routes and the complete sitemap at a modest rate. Confirm 200 responses, working images, proper 404s and no recurring 1102 errors. Check Cloudflare CPU/memory metrics; do not infer a precise CPU saving from local timing.
2. In a browser, visit Home → Product → Cart → Products in both languages. Confirm the route's canonical/description and that public pages return to indexable while cart/order pages stay excluded. Test a plan URL and the current checkout without creating a paid test order.
3. Verify Google Search Console ownership and submit the existing sitemap URL. Inspect representative Arabic/English pages and the new guides. Confirm Google can render catalog dependencies. Add Bing Webmaster Tools using verified site ownership. No Search Console or Bing submissions were performed in this session.
4. Validate Product/Article/Breadcrumb data against visible current prices and plans. Check source facts and eligibility before any Merchant Center feed. Do not promise FAQ rich results or AI citations.
5. Confirm Cloudflare Analytics is receiving data. Establish the actual baseline: non-brand impressions, clicks, indexed product pages, organic visits, verified purchases, conversion rate and verified revenue. The public Meta Pixel setting was empty at audit time; there is no evidence here of an active Meta conversion setup.
